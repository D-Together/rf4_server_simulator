## Problem Statement

玩家希望搏鱼时每 5 秒在聊天框看到「当前鱼还剩多少耐力」，开关放在钓具助手里，且只在当前手持竿进入搏鱼环节时播报。但服务端目前**拿不到真实的剩余耐力**：鱼的体力消耗由客户端按 `14/14` 下发的 `obj27.f5`（体力池）与 `f6`（初始体力比率）逐帧本地模拟，服务端既不接收也不保存当前值；`14/8` 负载上报只做数值观测，哪个槽位是鱼拉力/体力尚无第二份证据。直接播报服务端估算值会与客户端体力条不一致，属于无报文依据的自造状态。

## Solution

先用实机报文确认 `14/8` 中承载「当前体力/载荷」的真实槽位与量纲，再基于该真实值实现播报。阶段一交付一键采集与自动分析工具，不改服务端结算逻辑；阶段二在钓具助手加独立开关，搏鱼期间每 5 秒用临时聊天推送播报真实剩余耐力，不落库、不进个人消息列表。

## User Stories

1. 作为玩家，我在钓具助手一级菜单发送「2」进入耐力播报二级菜单，按「y」开启播报，之后每次搏鱼每 5 秒在聊天框看到当前鱼的剩余耐力；数值来自客户端上报的真实值，不是服务端估算。
2. 作为玩家，在二级菜单按「n」关闭、「h」看说明、「b」返回一级；默认关闭，重登后保留设置，与「满红不爆」开关互不影响。
3. 边界：仅当**当前手持竿**处于「已中钩且未结算」时播报；收竿、跑鱼、断件、换竿、下线立即停止；未开启或不在搏鱼态时零推送；多竿并存时只播手持竿。
4. 边界：播报不写 `mail` 表、不改结算与磨损、不重推鱼实体；重连或重复开启不产生重复播报。

## Implementation Decisions

### 阶段一（本轮，取证）

- `tools/capture_fight_load.ps1`：默认在 gameserver 工作目录的 **`data/` 子目录**（由运行中的 launcher 进程路径自动探测，也可用 `-DataDir` 覆盖）放 `trace_cmds.on` 与 `trace_full.on` 哨兵（`trace.go` 把 hex 上限从 160 放宽到 4096）→ 重启 gameserver → 调 `tools/trace.ps1 -Filter '14/8'` 抓一次完整搏鱼 → 结束后恢复哨兵原状。若两个哨兵已存在且 gameserver 在其之后启动，用 `-NoRestart` 跳过全部哨兵操作与重启，不断线。仅新增工具脚本，不改 Go 代码。
- `tools/analyze_fight_load.py`：从 trace 文本提取 `TRACE 收 cmd=14/8` 的 hex 帧，按 4 字节滑动窗口以 float32 / int32 / uint32 小端解码，跨帧统计单调递减比例与首末差，输出候选偏移与逐帧数值表；`--selftest` 用合成帧自证能挑出已知槽位。刻意做成字节级扫描，因为 `14/8` 字段布局正是要找的东西。整数窗口与浮点字节重叠会产生伪候选，脚本按相对变化幅度排序并把这类候选标注 `overlap?` 降权，浮点槽位优先。另加 `--min-coverage`（下降步数占全部相邻步的比例）与 `--max-last-share`（末帧跳变占全降幅的比例）两道过滤：官服样本里 `2.01/2.00/…→0.59` 这种末帧状态翻转曾被旧版误判成"耐力持续消耗"，必须排除。
- 交叉证据：本竿渔轮损伤日志的 `load_fields`（`fightLoadProbe.logFields` 已有 path/kind/n/min/max/last）用来验证候选槽位的首末值方向。
- 未确认字段前**不**改 `recordFightReelLoad`、不把 `14/8` 数值写进磨损账，遵守 `specs/changes/reel-friction-life-model/spec.md`「先观测不结算」。

### 阶段二（已实现）

- 开关：复用 `kv` 表，key `gear-assistant:stamina-report:<uid>`（值 `"1"/"0"`，默认关）；钓具助手为两级菜单：一级列出 `1 【满红不爆】` / `2 【耐力播报】`，发序号（或名称 `过载`/`耐力`）进入对应二级；二级只认 `y`(开)/`n`(关)/`h`(说明)/`b`(返回)，其余输入重显本菜单。二级状态按 uid 存在进程内（`Server.gearMenuState`，重启即回一级），开关本身仍落 kv。回复复用联系人 UID `2147483646` 与 `19/1` 链路；`readKVFlag` 与满红不爆共用读取逻辑，设置写入与回复邮件仍走同一事务（`insertContactReply`）。两个开关互不影响。
- 数值：`fishStaminaFromLoad` 从 `14/8` 原始 body 偏移 45 读 F32 小端值，校验 `[0,1]` 与有限性；`fishRigLimitFromLoad` 从偏移 49 读钓组最弱环 kgf，校验 `(0,500]` 与有限性。两者只用于播报，不进结算、不进磨损账、不改 `obj27` 形状。
- 播报条件：`st.Hooked && st.Pending != nil && st.CastActive && !st.Resolved`，且 `s.fishingState(uid) == st`（当前手持竿）。
- 节拍：**不另起 ticker**，以每约 2 秒到达的 `14/8` 为心跳做 5 秒节流（`FishState.lastStaminaReportAt` / `lastStaminaFishGUID` 两个进程内字段，不进持久化快照）。搏鱼结束、换竿、掉线后自然停止，无 goroutine 或定时器需回收；每尾新鱼首帧立即播报。
- 超载率：`超载 = max(0, (剩余体力 × 标定拉力 − 钓组最弱环) ÷ 钓组最弱环) × 100`。分子用 `fishFightPullKgfFor`（与 `27#8` 同源），分母用帧内 `.1.5`（与服务端 `gearBreakLimitKg` 逐位一致），不查装备库。拉得动时为 0%，体力耗尽时分子归零。
- 播报通道：`sess.Push(24, 27, buildChatEchoPush(...))`，与 `notifyFishHooked` 同通道；不写 `mail` 表、不用 24/10 公聊；文案 `[耐力] NN.N% · [超载] NN%`，帧内读不到最弱环或该鱼种无标定拉力时退化为 `[耐力] NN.N%`。
- 兼容：客户端基线 `4.0.25034`；不改 `14/14` / `24/27` 响应形状、不改表结构、不加迁移；回滚只需移除 `recordFightReelLoad` 末尾一行调用，kv 旧值无害。

## Testing Decisions

- 阶段一：分析脚本用**手造**合成帧（已知 float32 槽位按固定步长递减、另设递增计数器作对照、其余恒定）验证能挑出正确偏移与方向；期望值来自字面量，不是复用解析代码再算一遍。截断帧（`…+K`）必须报警而非静默分析。
- 阶段二（已实现）：`gear_assistant_stamina_test.go` 按抓包确认的偏移（138 字节帧、offset 45 体力 / offset 49 钓组最弱环，均 F32 小端）合成帧，测 `fishStaminaFromLoad` 与 `fishRigLimitFromLoad`（含短帧/越界/NaN/非正值拒绝）、`fishOverloadPct`（小鱼恒 0%、大鱼为正、体力耗尽归零、分母或鱼缺失不出数）、两级菜单的开关指令与幂等、默认关、玩家隔离、重连保留、与满红不爆互不影响、一级菜单列出双开关；行为测「开关关/非手持竿/非搏鱼态/短帧零推送」「小鱼 `[耐力] 100.0% · [超载] 0%`」「同鱼耐力降到 37.1% 仍为 0%」「20kg 鱼出正超载」「帧内无最弱环时只报耐力」「5 秒节流」「换鱼立即播报」「24/27 形状」「不写 mail 表」。
- 实机验收：开启开关完整搏鱼一次，聊天框每 5 秒一条、数值趋势与客户端体力条一致；关闭后零推送；多竿切换只播手持竿。
- 回滚后变红：阶段二的开关与播报行为测试；阶段一脚本不受服务端回滚影响。

- 不新增协议字段、不改命令响应形状、不改客户端或 HUD、不新增独立助手联系人。

- `[事实]` 共享包 `official_trace.7z` 含 75 个文件：11 个官方 `14/14` 发鱼帧、约 50 个 `4/22` 装备快照、6 份解密 TRACE、`sim_compare.tsv` 的 f5/f6/f8/f19/f20/f21 逐样本对拍，以及 README/HANDOFF 里已有的体力池标定成果。

### 14/8 字段澄清与负荷率播报（2026-11-12）

- `[事实]` 用 `2026-11-07~12` 的 4671 帧完整 `14/8`（`len=138`）离线解码，按 >20s 间隔切成场次、与 `catch_log` 对时，确认 offset 45 的体力**确实单调下降**，只是慢且加速：45.36kg polyprion 527s 从 1.0000→0.3270（入户）；18.47kg n.pike 453s→0.1240（入户）；65.55kg 555s 结束时仍有 0.7695。前 2 分钟斜率仅约 0.0016%/s，配合 5 秒节流与整数百分比显示会看起来"卡在 100%"，这是此前误判为"不下降"的原因。
- `[事实]` 该帧的 12 个 F32 字段是一条从 offset 29 开始的连续数组，锚点反查结果：`.1.2`(37)=鱼重 kg、`.1.3`(41)=累计出线 mm、`.1.4`(45)=剩余体力、`.1.5`(49)=钓组最弱环 kgf、`.1.6`(53)=张力÷最弱环、`.1.7`(57)=当前张力 kgf，`.1.8/.1.9`(61/65) 为另外两个张力分量。

- `[推断]` 之前把 `.1.6` 当成"挣扎强度"是误读：它随张力抖动，而张力又受泄力封顶（14.8kg n.pike 那场制动力 9.42、`.1.7` 峰值 9.86），鱼乏了张力回落 → `.1.6` 从 0.90 降到 0.19，归零即入户。这与玩家"小鱼满体力也能拉、大鱼要磨到很低"的手感一致。
